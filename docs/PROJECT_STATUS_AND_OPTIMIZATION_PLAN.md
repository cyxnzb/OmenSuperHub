# OmenSuperHub 项目现状与优化计划（2026-10-08）

> 范围：当前 fork 的 `master@bec3e734c02e`。本文为**代码静态审阅 + 迭代计划**，不是实机性能结论；不包含硬件控制改动。
> 目标：稳定、安全、轻量、常用操作直达、专业功能可用。保留离线、无广告与传统托盘控制优势。
> 已有专项基线：[`STABILITY_ROADMAP.md`](STABILITY_ROADMAP.md)、[`UAT_THERMAL_STABILITY.md`](UAT_THERMAL_STABILITY.md)。

## 1. 当前已落地的能力与工程基础

| 模块 | 当前实现（从代码确认） | 边界 |
|---|---|---|
| 平台兼容/权限 | BIOS WMI、OEM SDK、PawnIO、模型/能力探测 | 主机型与 BIOS/驱动组合决定是否生效；不能从编译推断兼容 |
| 性能控制 | 内置及自定义预设、CPU 功率、GPU TGP/PPAB、DB、显卡模式、进阶调校 | 低层设置不保证所有硬件支持，需求区分期望值和实效值 |
| 风扇 | 自动/最大/固定转速、曲线编辑/导入、多级温度响应、过热保护 | 仍需不同负载/监控开关下的实机验证 |
| 监控 | CPU/GPU 温度/功率/频率、风扇转速、托盘/浮窗、刷新率设置 | 当前有效性与数据显示语义尚可改进 |
| 设备 | 灯光、OMEN 键、开机自启、配置持久化 | 多数路径和 UI/硬件调度仍强耦合 |
| 工程 | .NET Framework 4.8、Windows x64 CI、日志、超时感知外部进程 | 只有 Release 构建/仓库清洁门禁，缺确定性纯逻辑测试及硬件自动化 |

最近已合并：#60-#64 稳定性基础；#58 温控/性能审计（2026-09-30）；#66 CI 去重；#67 功耗调校简化（2026-09-30）。不要重复执行已合并改动。#58 的合并提交描述本地硬件 UAT 完成，但仓库无跨机型、可重复的基准证据；需保留持续回归门槛。

## 2. 风险台账（证据强度）

**P0-1 监控开关与风控采样耦合 [代码确认，影响待验证]**  
`Program.Config.cs:GetFanSpeedForTemperature()` 依据 `monitorCPU/monitorGPU` 决定温度是否参与查表；`RestoreConfig` 中两项同时关闭时会关闭硬件监控子进程。这意味着「不显示某项监控」与「不采集风控温度」之间没有清晰边界。先复现切换监控开关对自动风扇、安全兜底的影响；目标是**只隐藏显示不损害风控**，并为真正暂停采样提供安全规则。禁止在仍采用软件风控时让两个必需温度源均被用户无提示关闭。

**P0-2 自动风扇定时回调未显式防重入 [代码风险，待压力验证]**  
`Program.cs` 通过每 1 s 的 `System.Threading.Timer` 调用 `ApplyAutomaticFanControl()`，与同步 BIOS WMI 通道交互。虽然 BIOS WMI 有锁，控制回调本身未见独立防重入/命令合并。若单次调用超过周期，后续调用可能排队或争用；须记录实际延迟、重叠和风扇写入次数后采取单一在途/最新目标合并策略，并让紧急保护不被低优先级请求阻塞。

**P1-1 无效遥测的语义仍不统一 [代码确认]**  
`Program.cs` 维护 `CPUTemp/GPUTemp` 初始占位值（50/40），GPU 失去数据时存在 `GPUTemp = 40`，无效功率存在用 `0` 清空的路径。部分浮窗逻辑已用 ready 状态掩盖，但不是统一的数据模型。改为 `Value + Validity + Source + SampleTime` 快照，显示「-- / 数据不可用 / 休眠未唤醒」，正常的 0 W 必须与读取失败区分；风控只读通过质量检查的快照。

**P1-2 设置值不等于硬件生效值 [代码确认，后果待验证]**  
`Program.PowerTuningUx.cs` 的 CPU/DB/GPU 状态摘要主要由用户设置字符串和平台能力推导；`OmenHardware.SetCpuPowerLimit` / `SetGpuPowerState` 等以 BIOS WMI 写入为主，结果没有统一的确认/读取回执。需建立 `Requested / Applying / Effective / Unsupported / Failed` 状态；允许的设备采用读取回证，无反馈设备明确标示“已提交，未验证”，不得把按钮勾选当成硬件证据。

**P1-3 生命周期、状态与 UI 耦合 [代码确认]**  
`Program.cs` 集中处理监控子进程、线程定时器、休眠/电源恢复、托盘展示和异常恢复；`Program.Menu.cs`、`Program.Config.cs` 均为大型文件；`Program.PowerTuningUx.cs` 通过 `Application.Idle` 注入菜单。监控进程的退出重启存在延迟回调，需要排查退出/重启竞态。建议渐进引入服务边界，不做一次性重写。

**P2-1 入口深、术语过专业 [代码确认 + 上游社区反馈]**  
`Program.Menu.cs` 的风扇、性能、显卡、灯光等大量子菜单与调节项造成查找成本；#67 已新增简化功耗入口，但实现并未整体减少菜单层级。可参考上游讨论 https://github.com/breadeding/OmenSuperHub/discussions ，默认仅展现常用项、按能力隐藏不适用功能，进阶页保留全部原能力。

**P2-2 轮询效率待量化 [代码确认，非性能实测]**  
当前存在 100 ms UI/Omen 键检查、250 ms/1 s 遥测显示、每 1 s 自动风扇、30 s 维护任务等多频率周期工作。社区曾反馈 SYSTEM 进程占用，见 https://github.com/breadeding/OmenSuperHub/issues/40 。不先武断认为异常，先区分主进程/监控子进程/驱动/OS System CPU、唤醒、内存、磁盘写入，在相同负载与 OGH/上游基线下比较。

**文档问题 [确认]**  
现有 `STABILITY_ROADMAP.md` 把 #58 描述为“待 UAT 才能合并”，但该 PR 已于 2026-09-30 合并。应及时同步现实进度，并将“已实施”和“仍需跨硬件验证”分开。

## 3. 五维度路线与取舍

| 维度 | 应做（优先） | 暂不做 |
|---|---|---|
| 功能 | 能力检测、应用结果状态、可靠恢复、简化模式、诊断导出 | 广泛新硬件控制项、FPS/宏/云账号 |
| 性能 | 不重入/去重、按需轮询、减少不必要 WMI/进程调用、空闲资源评测 | 用降低安全采样频率换取低占用 |
| 实用性 | 开箱预设、设备支持情况/不可用原因、配置备份与恢复、防误操作 | 未经验证的“智能超频” |
| 用户体验 | 日常项直达、普通/高级分层、设置与实际效果区分、一致的警告与恢复说明 | 在每个菜单加更多二级配置 |
| 外观 | 保留系统托盘，统一字号/间距/明暗/图标；可选轻量概览面板 | 大型 Web UI、全量 WinForms/WPF 框架迁移 |

### 交互建议（方案，非现状）

- **托盘默认入口**：当前状态 → 性能预设 → 风扇（自动/安静/强劲） → 简要监控/打开概览 → 设置与帮助。
- **高级设置单独入口**：CPU PL1/PL2、IccMax、AC Load Line、GPU 超频、dState、DB 阈值、曲线编辑与排错工具。
- **状态文案**：明确「自动软件调速 / BIOS 自动 / 固定转速 / 最大散热 / 传感器不可用」「平台上限 / 用户请求 / 实际读回」。
- **可选极简概览窗口**：CPU、GPU 温度和功率、当前模式、风扇状态、仅 1–2 个快捷动作；不强制常驻。不以视觉翻新换取功耗增加。

## 4. 执行阶段、验收与止损

### S0 整理基线（文档 + 测量，所有代码改动前）

1. 确认 `master`、CI、依赖、可用硬件、支持边界、上游差异和已有 UAT 结果；修订旧文档状态。
2. 建立 UAT 基线记录格式：机型/CPU/GPU/BIOS/驱动/Windows/供电/室温/提交号/监控设置。
3. 对照 HWiNFO 等工具采集空闲 10 min、突发 CPU/GPU 负载、游戏/持续 10 min、降温 5 min、睡眠恢复、AC 插拔，记录原始温度、显示温度、风扇目标/实测 RPM、写入/读取失败与资源消耗。
4. 保存运行日志并建立问题分类：**已确认 / 代码风险待复现 / 体验机会 / 暂缓**。

**退出条件**：至少一个代表性设备有可重复日志及资源基线；没有设备数据时不宣称风控性能改善。

### S1 安全与正确性（P0，首个代码阶段）

- 解开 UI“显示监控”与安全风控采样开关的耦合；
- 风扇定时器控制串行/合并，保护紧急写入优先级，记录 WMI 调用延迟；
- 传感器失效/恢复使用有效性状态，杜绝有效 0°C 或伪装成 40°C 的可视读数；
- 断线、休眠、断电、应用退出时的风扇归属与恢复状态机；
- 针对风扇曲线校验、失效保护、平滑、迟滞、预设恢复写纯逻辑单测。

**验收**：`UAT_THERMAL_STABILITY.md` 全场景通过；无失效温度伪装有效数据；异常情况下明确交还 BIOS 或安全兜底；实机温度/声学表现不得较实测基线恶化。未通过立即回滚代码，不扩大优化范围。

### S2 真实生效与性能（P1）

- 硬件写入返回结构化结果；支持读回时区分“申请”和“生效”；
- 为监控子进程引入可取消的生命周期和有界重启策略；
- 观察主程序、监控子进程、WMI、SYSTEM 进程负载，缩减**重复**采样而非削弱风控；
- 系统待机、设备休眠、电池供电、监控面板关闭分别测 CPU/P95 响应、内存、唤醒/句柄增长与磁盘写入。

**验收**：CI 构建 + 单测通过；UI 操作不因重查询卡住；温控响应不退化；与 S0 同机同条件对比资源消耗，有实测改善才宣称“更轻量”。

### S3 用户体验与视觉（P1/P2）

- 默认菜单按常用任务重排、高级能力单独分层、明确不可用原因；
- 预设和风扇状态反馈、失败提示及一键恢复默认；
- 优化托盘/浮窗/风扇曲线编辑器的字体、间距、对比度和高 DPI；视觉稿先评审；
- 只有在托盘仍显拥挤且性能预算可接受时，才做可选轻量概览面板。

**验收**：普通用户能在不进入高级菜单的前提下完成“看温度—换预设—切风扇模式—恢复默认”；中英繁文本完整；125%/150%/200% DPI 下不截断；概览窗口关闭后额外轮询与常驻开销不可明显增加。

### S4 结构维护/发布（P2，渐进）

- 逐步抽出 `HardwareMonitorService` / `FanControlService` / `PresetService` / `HardwareTransport` / `SettingsService`，每次只抽离一个边界并保持原外部行为；
- CI 从仅编译升级为纯逻辑单测 + Release x64 构建 + 文档/静态校验；硬件验证仍需实机；
- 补充支持/已验证硬件矩阵、变更日志、故障诊断与回退指南；
- 框架升级、常驻服务拆分、驱动换代仅在收益与兼容性被验证后另行评估。

## 5. 决策门槛

1. **S1 必须先于 S3**：实际热行为未稳定前不调整风扇曲线参数和新 UI 预设。
2. **不复写上游**：上游同步先做差异检查，重点保护 #58/#67 功能与既有用户配置。
3. **不再仅凭主观温感调参**：温度准确性以机型匹配且配置一致的参考监控为依据，保留原始数据。
4. **硬件写操作有失败路径**：不支持/失败不等于成功；文案不可夸大。
5. **默认不增加常驻成本**：新面板、采集或诊断只在需要时启动。
6. **高风险操作留回滚**：风扇、功率、驱动、BIOS WMI 改动必须独立 PR，附对比证据与 UAT 记录。
7. **新增功能需要用户场景与价值证明**：不以竞品功能数量作为目标。

## 7. 需要人工硬件验证而非代码推断的项

- 不同 BIOS/机型的 CPU Package/Tctl 与 GPU Core 对应关系；
- 风扇命令能否读回、各机型最大转速与三风扇能力；
- 不同采样速度对温度峰值、控温效果、噪声的影响；
- 睡眠/唤醒、断电、监控退出及 OGH 冲突；
- 操作系统 SYSTEM 资源占用是否由本程序导致；
- 完整功率状态是否被 BIOS、EC、适配器、动态分配策略覆盖。

**最终判断**：显著优化潜力集中在“可靠性/状态正确性—性能成本—入口简化”三条主线；纯外观翻新是后续增益项，广泛新增功能暂缓。
